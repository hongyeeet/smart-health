### Medicine scanner: text reader (OCR) switch, set to OFF for testing (2026-10-12, later)

Joely asked for the scanner to run without the local text reader. New setting `SCAN_OCR_ENABLED` (default **true**; `.env.example` documents it; Joely's local `.env` now says `false`, so remove that line to switch it back). With it off: the photo goes to Gemini as it is (label name, ID, clinic address and phone visible to the model; this breaks the "names never go to a model" rule in `ai-models.md` section 6 for as long as it is off), the model's answer is scored without the text-reader cross-check, a "Prescribed by" line that is really the patient's name is dropped from the answer, and the **real photo is never stored**: a small grey square carrying the photo's checksum is kept instead (`scan_privacy.unmasked_photo`, `placeholder_photo`; `scan_extractor.extract_scan(ocr_enabled=...)`). The model is unchanged (`gemini-3.8-flash`). Comparison results behind this (two runs, 11 photos): Flash with OCR and Pro without OCR tied on accuracy; without OCR one wrong value (a start date) went through unflagged in one run and three in the other, so the text-reader check does catch mistakes. Tests added in `tests/unit/test_scan_extractor.py`. Test scans on `demo`: one holding the patient name was deleted; two later ones (empagliflozin, atorvastatin) carry no name.

Follow-up the same evening: Joely saw "We could not read this" on a label and thought the scanner only accepts medicines it has seen before. It does not: the scan code has no list of known drugs and never rejects a medicine for being new (checked in `scan_confidence.decide`, and six unseen labels all read through the real API in 12 to 26 seconds). The cause was time. One read took 176 seconds (four tries of 45 s) while the web app gives up after 60 s, so the screen said it could not read it although the server finished; a retake was faster, which looked like "it worked because it had seen it before". Fixed: the scan model client now cuts a stalled call at 40 s and tries once more (worst case about 85 s), the web app waits 100 s, and a timeout says "Reading the label is taking longer than usual" instead of "We could not read this".
